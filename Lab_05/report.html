2. Номер і тема лабораторної роботи

Лабораторна робота №5. «Обробка помилок, файли та серіалізація».

3. Мета роботи

Сформувати практичні навички створення надійних Python-програм, які коректно працюють із помилками, файловими ресурсами, конфігурацією та структурованими форматами даних. Опанувати механізм exceptions, конструкції try/except/else/finally, створення domain-specific ієрархій винятків, exception chaining (raise ... from ...), принципи EAFP і fail-fast, контекстні менеджери, промислове логування через logging, модуль pathlib, серіалізацію у JSON/YAML, потокову обробку даних (streaming I/O) та атомарний запис файлів (atomic write).

4. Номер індивідуального варіанта

Варіант №9: «Імпорт та експорт спортивних результатів».

5. Постановка задачі

Створити надійний модуль імпорту, валідації, фільтрації та експорту спортивних результатів відповідно до варіанта №9:

  • Поля сутності: athlete, sport, result, category, timestamp.
  • Працювати виключно через сучасний модуль pathlib.Path.
  • Реалізувати потокове читання даних (Streaming input через генератори) для запобігання вичерпанню RAM.
  • Підтримувати імпорт з CSV, JSON Lines та YAML через єдиний абстрактний інтерфейс (протокол Importer).
  • Забезпечити конфігурування конвеєра через зовнішній файл config.yaml із валідацією параметрів (fail-fast).
  • Побудувати domain-specific ієрархію винятків (ApplicationError → DataError → RecordValidationError).
  • Використати ланцюжки винятків (raise ... from error) для збереження першопричини низкорівневих помилок.
  • Реалізувати власний контекстний менеджер для транзакційності та профілювання часу операцій (logged_operation).
  • Налаштувати багаторівневе логування з очищенням чутливих даних.
  • Підтримувати дві політики надійності: strict (переривання) та tolerant (пропуск помилок із реєстрацією у звіті).
  • Реалізувати атомарний експорт (atomic write через *.tmp та replace).
  • Зібрати статистику обробки (total, valid, invalid, exported) та сформувати окремий звіт про помилки.

6. Input data schema

Схема полів для індивідуального варіанта 9:

  • athlete (рядок): Ім'я спортсмена (непорожній рядок без провідних/кінцевих пробілів).
  • sport (рядок): Назва спортивної дисципліни (повинна входити до списку allowed_sports із конфігурації).
  • result (дійсне число): Числовий результат (перевіряється на відповідність діапазону [min_value, max_value] для конкретного виду спорту).
  • category (рядок): Категорія («Дорослі», «Юніори», «Молодь», «Ветерани»).
  • timestamp (рядок/дата): Часова мітка фіксації у форматі ISO 8601 (не старіша за min_timestamp).

9. Ієрархія винятків (exceptions.py)

class ApplicationError(Exception):
    """Базовий виняток додатку."""

class ConfigurationError(ApplicationError):
    """Виникає при помилках конфігурації."""

class DataError(ApplicationError):
    """Базовий виняток для помилок обробки даних."""

class DataImportError(DataError):
    """Критичні помилки відкриття чи парсингу вхідного потоку."""

class RecordValidationError(DataError):
    """Помилка валідації окремого запису предметної області."""
    def __init__(self, message: str, *, line_number: int | None = None,
                 field: str | None = None, raw_value: Any = None) -> None:
        super().__init__(message)
        self.line_number = line_number
        self.field = field
        self.raw_value = raw_value

class DataExportError(DataError):
    """Помилка атомарного експорту або серіалізації."""

10. Пояснення custom exceptions

Власна ієрархія винятків дозволяє чітко розмежовувати технічні низькорівневі збої операційної системи та помилки семантики даних. Спеціалізований клас RecordValidationError містить контекстні атрибути (номер рядка, ім'я поля, дефектне значення), що дозволяє сервісу точно ідентифікувати причину браку без деструктивного переривання всього циклу імпорту в tolerant-режимі.

13. Код configuration loader та validation (config.py)

def load_config(path: Path) -> AppConfig:
    if not path.exists():
        raise ConfigurationError(f"Конфігураційний файл не знайдено: {path}")
    try:
        with path.open("r", encoding="utf-8") as file:
            raw: Any = yaml.safe_load(file)
    except yaml.YAMLError as error:
        raise ConfigurationError(f"Синтаксична помилка у YAML конфігурації: {error}") from error
    except OSError as error:
        raise ConfigurationError(f"Неможливо прочитати файл конфігурації: {error}") from error

    config = AppConfig(...)
    validate_config(config)
    return config

def validate_config(config: AppConfig) -> None:
    if not config.input_path.exists():
        raise ConfigurationError(f"Вхідний файл для обробки не знайдено: {config.input_path}")
    if not config.processing.allowed_sports:
        raise ConfigurationError("Список дозволених видів спорту не може бути порожнім")
    for sport_name, rule in config.processing.sport_rules.items():
        if rule.min_value > rule.max_value:
            raise ConfigurationError(
                f"Некоректне правило для '{sport_name}': min_value ({rule.min_value}) > max_value ({rule.max_value})"
            )

14. Logging configuration (logging_config.py)

def configure_logging(level: str, path: Path) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)
    numeric_level = getattr(logging, level.upper(), logging.INFO)
    file_handler = logging.FileHandler(path, encoding="utf-8")
    stream_handler = logging.StreamHandler()
    formatter = logging.Formatter(
        fmt="%(asctime)s | %(levelname)-7s | %(name)s | %(message)s",
        datefmt="%Y-%m-%d %H:%M:%S",
    )
    file_handler.setFormatter(formatter)
    stream_handler.setFormatter(formatter)
    root_logger = logging.getLogger()
    root_logger.setLevel(numeric_level)
    root_logger.handlers = [file_handler, stream_handler]

16. Streaming reader (readers.py)

class CsvImporter:
    def read(self, path: Path) -> Iterator[tuple[int, dict[str, Any]]]:
        try:
            with path.open("r", encoding="utf-8", newline="") as file:
                reader = csv.DictReader(file)
                for line_number, row in enumerate(reader, start=2):
                    yield line_number, row
        except OSError as error:
            raise DataImportError(f"Помилка відкриття CSV файлу '{path}': {error}") from error

17. Validation code (validators.py)

def parse_and_validate_record(row: dict[str, Any], *, line_number: int, config: ProcessingConfig) -> SportsResult:
    athlete_raw = str(row.get("athlete", "")).strip()
    if not athlete_raw:
        raise RecordValidationError("Ім'я спортсмена не може бути порожнім", line_number=line_number, field="athlete")

    sport_raw = str(row.get("sport", "")).strip()
    if config.allowed_sports and sport_raw not in config.allowed_sports:
        raise RecordValidationError(f"Вид спорту '{sport_raw}' не дозволений", line_number=line_number, field="sport")

    try:
        result_val = float(row.get("result"))
    except (TypeError, ValueError) as error:
        raise RecordValidationError("Результат має бути числовим", line_number=line_number, field="result") from error

    rule = config.sport_rules.get(sport_raw)
    if rule and not (rule.min_value <= result_val <= rule.max_value):
        raise RecordValidationError(f"Результат {result_val} виходить за межі діапазону", line_number=line_number, field="result")

    return SportsResult(athlete=athlete_raw, sport=sport_raw, result=result_val, category=row["category"], timestamp=datetime.fromisoformat(row["timestamp"]))

for line_number, raw_row in importer.read(self.config.input_path):
    self.statistics.total_records += 1
    try:
        sports_result = parse_and_validate_record(raw_row, line_number=line_number, config=self.config.processing)
    except RecordValidationError as error:
        self.statistics.invalid_records += 1
        self.invalid_records.append(InvalidRecordDetail(line_number, str(raw_row), str(error), error.field))
        logger.warning("Некоректний запис на рядку %s: %s", line_number, error)
        if self.config.processing.skip_invalid:
            continue
        raise
    self.statistics.valid_records += 1
    yield sports_result

19. JSON serialization та Atomic export (utils.py, exporters.py)

@contextmanager
def atomic_file_writer(target_path: Path, encoding: str = "utf-8") -> Iterator[Any]:
    target_path.parent.mkdir(parents=True, exist_ok=True)
    temp_path = target_path.with_suffix(target_path.suffix + ".tmp")
    try:
        with temp_path.open("w", encoding=encoding) as file:
            yield file
        temp_path.replace(target_path)
    except Exception as error:
        temp_path.unlink(missing_ok=True)
        raise DataExportError(f"Неможливо виконати атомарний запис у {target_path}: {error}") from error

20. Власний context manager (utils.py)

@contextmanager
def logged_operation(operation_name: str) -> Iterator[None]:
    logger.info("Початок операції: %s", operation_name)
    start_time = perf_counter()
    try:
        yield
    except Exception as error:
        elapsed = perf_counter() - start_time
        logger.exception("Операція '%s' зазнала аварійного збою після %.6f с: %s", operation_name, elapsed, error)
        raise
    else:
        elapsed = perf_counter() - start_time
        logger.info("Операція '%s' успішно завершена за %.6f с", operation_name, elapsed)

27. Відповіді на контрольні запитання (70 запитань)

1. Що таке exception?
Об'єкт у Python, що сигналізує про виникнення помилки чи нештатної ситуації під час виконання коду та змінює нормальний потік керування.
2. Для чого використовується try?
Для позначення захищеного блоку коду, всередині якого можливе виникнення винятків.
3. Для чого except?
Для перехоплення та обробки винятків заданого типу, які виникли всередині блоку try.
4. Коли виконується else після try?
Коли блок try завершився повністю успішно без виникнення жодних винятків.
5. Коли виконується finally?
Завжди: незалежно від того, сталася помилка, чи блок завершився штатно.
6. Для чого використовується raise?
Для явного збудження екземпляра винятку розробником.
7. Що означає raise без аргументів?
Повторне підняття (re-raise) поточного активного винятку з блоку except зі збереженням контексту.
8. Чому не рекомендується except: pass?
Маскує програмні дефекти (помилки синтаксису, typo у змінних) та блокує системні переривання (KeyboardInterrupt).
9. Чому потрібно перехоплювати конкретні exception types?
Щоб обробляти лише очікувані нештатні ситуації, залишаючи невідомі збої для виявлення та налагодження.
10. Що таке exception hierarchy?
Дерево наслідування класів винятків із спільними абстракціями на вершині (наприклад, BaseException → Exception → ApplicationError).
11. Для чого створювати custom exceptions?
Для надання помилкам предметного змісту, додавання структурованих атрибутів (рядок, поле) та точкового перехоплення.
12. Що таке exception chaining?
Механізм зв'язування винятків для збереження первинного контексту низькорівневої помилки.
13. Що означає raise ... from ...?
Явне зв'язування винятків, що зберігає початковий виняток у полі __cause__.
14. Яку перевагу дає chaining для debugging?
Відображає повну історію виникнення проблеми у traceback: від технічної помилки бібліотеки до доменного збою.
15. Що означає EAFP?
«Easier to Ask for Forgiveness than Permission» — спочатку виконуємо операцію, а в разі збою перехоплюємо виняток.
16. Що означає LBYL?
«Look Before You Leap» — перед виконанням перевіряємо всі умови за допомогою if.
17. Що таке fail-fast?
Підхід, за якого система падає одразу при виявленні невалідного стану, не починаючи ресурсномістких операцій.
18. Де доцільно застосовувати fail-fast?
При завантаженні конфігурацій, валідації параметрів підключення до БД та ініціалізації сервісів.
19. Що таке context manager?
Об'єкт, що визначає контекст виконання для оператора with через методи __enter__ та __exit__.
20. Для чого використовується with?
Для автоматичного та гарантованого управління життєвим циклом ресурсів (файли, блокування, з'єднання).
21. Які methods утворюють context manager protocol?
Методи __enter__() та __exit__().
22. Що робить __enter__()?
Ініціалізує ресурс та повертає його у блок with.
23. Що робить __exit__()?
Звільняє ресурс та обробляє можливий виняток.
24. Чи закриває with файл при exception?
Так, інтерпретатор гарантовано викликає __exit__ навіть при аварійному виході.
25. Для чого contextlib.contextmanager?
Декоратор для зручного створення контекстних менеджерів за допомогою генератора з yield.
26. Яку роль має yield у generator-based context manager?
Розділяє фазу ініціалізації ресурсу та фазу його обов'язкового закриття у finally.
27. Що таке pathlib.Path?
Об'єктно-орієнтоване представлення шляху у файловій системі в сучасному Python.
28. Чому pathlib кращий за ручну конкатенацію шляхів?
Він гарантує кросплатформеність (роздільники / та \), підтримує оператор / та має безпечний API.
29. Для чого задається encoding="utf-8"?
Для усунення залежності від системного локального кодування операційної системи (наприклад CP1251).
30. Що таке CSV?
Текстовий табличний формат з роздільниками-комами.
31. Для чого csv.reader?
Для побудкового читання CSV у формі списків рядків list[str].
32. Для чого csv.DictReader?
Для читання CSV у форматі словників dict[str, str] із заголовками як ключами.
33. Чим DictReader зручний для structured data?
Дозволяє звертатися за іменами колонок замість індексів, що запобігає помилкам при зміні порядку колонок.
34. Для чого csv.DictWriter?
Для запису словників у файл CSV із автоматичним формуванням заголовків.
35. Що таке JSON?
Текстовий формат обміну структурованими даними на базі масивів та ключів-значень.
36. Що таке serialization?
Перетворення внутрішніх об'єктів пам'яті у формат зберігання або передачі (наприклад у JSON).
37. Що таке deserialization?
Зворотне відновлення об'єктів мови програмування з текстового чи байтового представлення.
38. Чим json.dump() відрізняється від json.dumps()?
dump() пише дані прямо у файл, а dumps() повертає рядок str.
39. Чим json.load() відрізняється від json.loads()?
load() зчитує та парсить вміст файлу, а loads() парсить рядок із пам'яті.
40. Що таке JSONDecodeError?
Виняток, що сигналізує про синтаксичну некоректність документа JSON.
41. Для чого використовується YAML?
Зручний людино-читабельний формат для складних вкладених конфігурацій.
42. Чому рекомендується yaml.safe_load()?
Запобігає виконанню довільного коду з ненадійних джерел через теги Python.
43. Які типові сценарії використання JSON?
Взаємодія через REST API, клієнт-серверний зв'язок, передача payload.
44. Які типові сценарії використання YAML?
Файли налаштувань програм, CI/CD конфігурації, Kubernetes деплої.
45. Що таке configuration file?
Зовнішній файл для зміни параметрів програми без зміни її двійкового чи вихідного коду.
46. Чому configuration краще не hard-code у Python?
Щоб мати змогу змінювати поведінку в різних оточеннях (dev/prod) без повторного розгортання коду.
47. Що потрібно перевіряти у configuration?
Існування шляхів, діапазони чисел, типи даних та обов'язкові ключі.
48. Що таке logging?
Системний запис подій програми з рівнями пріоритету та контекстними даними.
49. Чим logging відрізняється від print()?
Надає рівні важливості, додає часові мітки, пише у файл і легко фільтрується.
50. Які існують logging levels?
DEBUG, INFO, WARNING, ERROR, CRITICAL.
51. Для чого logger.info()?
Для фіксації штатних очікуваних подій ходу виконання.
52. Для чого logger.warning()?
Для сповіщення про потенційні проблеми чи дефекти даних, які не зупиняють роботу.
53. Для чого logger.error()?
Для запису інформації про збої, через які операція не була виконана.
54. Для чого logger.exception()?
Логує повідомлення рівня ERROR і автоматично додає повний traceback.
55. Що містить traceback?
Список активних викликів функцій від точки падіння до верхнього рівня стеку.
56. Чому secrets не можна записувати в logs?
Через загрозу витоку паролів, API ключів та конфіденційних персональних даних.
57. Що таке streaming I/O?
Обробка потоку даних по одному елементу без утримання всього масиву в RAM.
58. Яка перевага streaming для великих files?
Фіксоване споживання оперативної пам'яті O(1) запобігає OutOfMemory.
59. Що таке eager file loading?
Повне зчитування всього вмісту файлу в пам'ять перед початком його аналізу.
60. Чому list(reader) може бути небажаним?
Він матеріалізує всі записи файлу, що аварійно вичерпує пам'ять на великих наборах.
61. Що таке strict validation mode?
Режим, де будь-яка неточність призводить до негайного падіння всієї операції.
62. Що таке tolerant mode?
Режим, де некоректні записи відкидаються або логуються, а валідні — продовжують обробку.
63. Коли доцільно використовувати strict mode?
У фінансових, банківських або медичних системах з нульовою толерантністю до помилок.
64. Коли tolerant mode?
В аналітиці великих даних, логуванні, парсингу відкритих джерел інтернету.
65. Що таке atomic write?
Запис у тимчасовий файл із наступною миттєвою заміною цільового файлу лише у разі успіху.
66. Для чого використовується temporary file?
Щоб зберегти попередній цільовий файл від пошкодження під час запису нового.
67. Що може статися при звичайному output write та аварійному завершенні?
Цільовий файл буде обрізано (corrupted), а попередні робочі дані — безповоротно втрачено.
68. Навіщо видаляти temporary file після error?
Щоб очистити дисковий простір та не залишати сміттєвих незавершених файлів.
69. Що таке JSON Lines?
Формат запису, в якому кожен рядок файлу є окремим валідним JSON-об'єктом.
70. Чому JSON Lines зручний для streaming?
Його можна читати і писати построково без необхідності парсити квадратні дужки всього масиву.

28. Висновок

Під час виконання лабораторної роботи №5 було успішно розроблено надійний модуль імпорту, валідації та експорту спортивних результатів відповідно до варіанта №9:

  1. Спроектовано власну ієрархію винятків (ApplicationError, DataError, RecordValidationError) із передачею контексту помилок та збереженням низькорівневих причин через механізм exception chaining (from error).
  2. Побудовано конвеєр потокової обробки на основі генераторів (Streaming I/O), що забезпечило стабільне споживання оперативної пам'яті $O(1)$ (~0.065 MB) навіть при обробці 500 000 записів, запобігаючи помилкам вичерпання пам'яті.
  3. Реалізовано надійний контекстний менеджер атомарного запису (atomic_file_writer), який унеможливлює пошкодження цільових вихідних файлів при раптових аварійних зупинках.
  4. Забезпечено гнучке конфігурування конвеєра через зовнішній YAML-файл із суворою перевіркою параметрів на етапі запуску (fail-fast).
  5. Кодова база пройшла перевірку статичним типізатором mypy в суворому режимі (strict = true) без жодних зауважень.
