## 5. Опис предметної області
Предметна область охоплює облік та аналіз досягнень спортсменів на різноманітних спортивних змаганнях. Система забезпечує реєстрацію спортсменів, видів спорту, турнірів та фіксацію індивідуальних результатів. Змагальні результати можуть мати різну метрику оцінювання (наприклад, бали, метри або секунди) та різні критерії лідерства (для одних видів спорту більший результат означає перемогу, для інших — менший час є кращим). Система формує рейтингові таблиці, розраховує агреговані статистичні показники та сповіщає зовнішні підсистеми про нові рекорди.

## 8. Пояснення inheritance (наслідування)
Наслідування використано для реалізації сімейства взаємозамінних алгоритмів сортування рейтингу (**Strategy Pattern**):
- Базовий абстрактний клас `RankingStrategy(ABC)` задає контракт методу `sort_results()`.
- Підкласи `HigherScoreWinsStrategy` та `LowerTimeWinsStrategy` успадковують базовий клас та реалізують специфічну логіку сортування (більший бал краще проти меншого часу).
- Це відповідає відношенню **is-a** («HigherScoreWinsStrategy є RankingStrategy») і принципу підстановки Лісков (LSP).

## 9. Пояснення composition (композиції)
Композиція реалізує зв'язок **has-a** і є гнучкішою за глибоке наслідування:
- Сутність `Result` компонується з окремих об'єктів `Athlete`, `Sport`, `Competition` та незмінного `Score`.
- Контейнер `RankingTable` містить у собі список результатів та стратегію ранжування `RankingStrategy`.
- `SportsAccountingService` компонується з репозиторіїв та інтерфейсів сповіщення/експорту.
Це забезпечує слабку зв'язаність компонентів (`low coupling`) і легкість тестування.

## 10. Приклад encapsulation (інкапсуляції)
Об'єкт сам контролює свій внутрішній стан і валідує будь-які зміни:
```python
class Result:
    # Захищене поле _score недоступне для прямого некоректного присвоєння
    _score: Score

    @property
    def score(self) -> Score:
        return self._score

    @score.setter
    def score(self, new_score: Score) -> None:
        if new_score.value < 0:
            raise ValueError("Result score cannot be negative.")
        self._score = new_score
```

## 13. Приклад immutable value object
Незмінний об'єкт значення `Score` гарантує незмінність стану (`frozen=True`, `slots=True`) та підтримує арифметичні операції над спортивними показниками:
```python
@dataclass(frozen=True, slots=True)
class Score:
    value: float
    unit: str = "pts"

    def __post_init__(self) -> None:
        if self.value < 0:
            raise ValueError(f"Score value cannot be negative: {self.value}")

    def __add__(self, other: "Score") -> "Score":
        if self.unit != other.unit:
            raise ValueError(f"Unit mismatch: {self.unit} != {other.unit}")
        return Score(round(self.value + other.value, 4), self.unit)
```

## 15. Приклад Protocol (структурний інтерфейс)
Протокол задає контракт у стилі статичної качиної типізації (`structural subtyping`):
```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Identifiable(Protocol):
    @property
    def id(self) -> int:
        ...

class Notifier(Protocol):
    def send(self, recipient: str, message: str) -> None:
        ...
```
Будь-який клас, що має метод `send(recipient, message)`, задовольняє протокол `Notifier` без явного успадкування.

## 16. Dunder methods (спеціальні методи)
У класах `RankingTable` та `Score` реалізовано ключові магічні методи:
1. `__len__(self)` — повертає кількість результатів у таблиці: `len(ranking_table)`;
2. `__iter__(self)` — дозволяє ітеруватись по відсортованій таблиці в циклі `for result in table:`;
3. `__contains__(self, item_id)` — перевірка наявності результату через оператор `in`: `101 in table`;
4. `__getitem__(self, index)` — доступ за індексом до лідерів: `table[0]`;
5. `__add__(self, other)` — додавання двох спортивних балів з перевіркою одиниць: `score1 + score2`;
6. `__str__(self)` та `__repr__(self)` — зручне строкове та налагоджувальне представлення об'єктів.

## 17. Generic class
Універсальний репозиторій для сутностей з доступом за $O(1)$:
```python
class InMemoryRepository(Generic[TEntity]):
    def __init__(self) -> None:
        self._items: dict[int, TEntity] = {}

    def add(self, entity: TEntity) -> None:
        self._items[entity.id] = entity

    def get(self, entity_id: int) -> TEntity | None:
        return self._items.get(entity_id)

    def all(self) -> list[TEntity]:
        return list(self._items.values())
```

## 22. Пояснення принципів SOLID у проєкті

1. **SRP (Single Responsibility Principle)**:
   - `Athlete`, `Result`, `Score` відповідають виключно за збереження стану та валідацію власних даних.
   - `RankingStrategy` відповідає лише за алгоритми сортування.
   - `SportsAccountingService` оркеструє бізнес-сценарії, делегуючи збереження репозиторіям, а сповіщення — нотифікаторам.
2. **OCP (Open/Closed Principle)**:
   - Додавання нового виду ранжування (наприклад, за сумою очок у багатоборстві) реалізується створенням нового класу-нащадка `RankingStrategy` без модифікації коду сервісу чи моделі результатів.
3. **LSP (Liskov Substitution Principle)**:
   - Класи `HigherScoreWinsStrategy` та `LowerTimeWinsStrategy` можуть прозоро підставлятися всюди, де очікується базовий `RankingStrategy`, не ламаючи поведінки системи.
4. **ISP (Interface Segregation Principle)**:
   - Інтерфейси розділені на невеликі вузькоспеціалізовані протоколи: `Identifiable`, `ScoredEntity`, `Notifier`, `ResultExporter`. Класи реалізують лише потрібні їм методи.
5. **DIP (Dependency Inversion Principle)**:
   - Високорівневий сервіс `SportsAccountingService` залежить від абстракцій `Notifier` та `ResultExporter`, а не від конкретних низькорівневих реалізацій відправки пошти чи запису в файл.

## 28. Контрольні запитання

### 1. Що таке class?
**Відповідь:** Клас — це шаблон (креслення), який описує структуру атрибутів та поведінку (методи) створюваних на його основі об'єктів.

### 2. Що таке object?
**Відповідь:** Об'єкт — це сутність у пам'яті комп'ютера, яка має стан, поведінку та унікальний ідентифікатор.

### 3. Що таке instance?
**Відповідь:** Екземпляр конкретного класу, створений за його описом.

### 4. Для чого `__init__()`?
**Відповідь:** Спеціальний метод-ініціалізатор, що налаштовує початковий стан екземпляра під час його створення.

### 5. Що таке instance attribute?
**Відповідь:** Атрибут, який прив'язаний до конкретного екземпляра об'єкта (зберігається в `self.__dict__`).

### 6. Що таке class attribute?
**Відповідь:** Атрибут, визначений на рівні самого класу, спільний для всіх його екземплярів.

### 7. Що таке encapsulation?
**Відповідь:** Принцип ООП, за яким внутрішній стан об'єкта захищається від прямого неконтрольованого зовнішнього втручання та змінюється лише через публічні методи.

### 8. Для чого properties?
**Відповідь:** Декоратор `@property` дозволяє звертатися до методу як до атрибута з можливістю контролю читання, зміни (`setter`) та видалення (`deleter`).

### 9. Чим property відрізняється від public field?
**Відповідь:** Доступ до звичайного поля не перевіряється, а property дозволяє виконувати валідацію та обчислення при присвоєнні або зчитуванні.

### 10. Що таке inheritance?
**Відповідь:** Механізм мови, що дозволяє одному класу успадкувати структуру й поведінку іншого класу для повторного використання або розширення.

### 11. Що означає relation is-a?
**Відповідь:** Відношення спеціалізації між класами (наприклад, `HigherScoreWinsStrategy is-a RankingStrategy`).

### 12. Що таке composition?
**Відповідь:** Принцип побудови складних об'єктів шляхом об'єднання простіших і незалежних об'єктів як своїх полів.

### 13. Що означає relation has-a?
**Відповідь:** Відношення володіння (наприклад, `Result has-a Athlete`, `Car has-an Engine`).

### 14. Коли composition краща за inheritance?
**Відповідь:** У більшості випадків проектування архітектури, коли поведінка може динамічно змінюватися під час виконання та потрібно уникнути жорсткої зв'язаності монолітних ієрархій наслідування.

### 15. Для чого super()?
**Відповідь:** Для виклику реалізації методів батьківського класу згідно з порядком MRO (Method Resolution Order).

### 16. Що таке polymorphism?
**Відповідь:** Здатність різнорідних об'єктів реалізовувати однаковий інтерфейс з власною специфічною поведінкою.

### 17. Що таке duck typing?
**Відповідь:** Принцип динамічної типізації: якщо об'єкт реалізує необхідний набір методів та властивостей, він вважається придатним для використання незалежно від його положення в ієрархії наслідування («якщо це плаває як качка і крякає як качка, то це качка»).

### 18. Що таке ABC?
**Відповідь:** Абстрактний базовий клас (`Abstract Base Class`), який не дозволяє створювати власні екземпляри і зобов'язує підкласи реалізувати методи, помічені `@abstractmethod`.

### 19. Для чого abstractmethod?
**Відповідь:** Декоратор, що позначає метод в ABC як обов'язковий до реалізації в усіх конкретних нащадках.

### 20. Чи можна створити instance abstract class?
**Відповідь:** Ні, спроба інстанціювати клас, що має нереалізовані абстрактні методи, викликає помилку `TypeError`.

### 21. Що таке Protocol?
**Відповідь:** Механізм структурної типізації (PEP 544), що дозволяє описувати інтерфейси без потреби явного успадкування.

### 22. Чим Protocol відрізняється від ABC?
**Відповідь:** ABC вимагає явного наслідування (номінальна типізація), а Protocol перевіряє лише відповідність сигнатур методів (структурна типізація).

### 23. Що таке structural typing?
**Відповідь:** Система типів, де сумісність визначається формою об'єкта (наявністю полів і методів), а не ім'ям його батьківського класу.

### 24. Що таке nominal typing?
**Відповідь:** Система типів, де сумісність перевіряється за явним деревом наслідування та назвою типу.

### 25. Що таке dataclass?
**Відповідь:** Декоратор стандартної бібліотеки, що автоматично генерує шаблонні методи класів (`__init__`, `__repr__`, `__eq__`) на основі оголошених анотацій типів.

### 26. Які methods генерує dataclass?
**Відповідь:** За замовчуванням: `__init__`, `__repr__`, `__eq__`, а за налаштуваннями — `__hash__`, `__lt__`, `__gt__` тощо.

### 27. Для чого default_factory?
**Відповідь:** Функція для безпечної ініціалізації змінюваних значень за замовчуванням (наприклад, `field(default_factory=list)`), щоб уникнути спільного використання одного екземпляра списку всіма об'єктами.

### 28. Чому mutable default є проблемою?
**Відповідь:** Якщо список чи словник оголошено як значення за замовчуванням у конструкторі, він створюється один раз під час завантаження модуля і модифікується спільно всіма екземплярами, спричиняючи приховані баги.

### 29. Для чого `__post_init__()`?
**Відповідь:** Хук у dataclass, що автоматично викликається після стандартного `__init__` для виконання додаткової валідації чи розрахунку похідних полів.

### 30. Що означає frozen=True?
**Відповідь:** Робить об'єкт датакласу незмінним (`immutable`): спроба змінити атрибут викликає виняток `FrozenInstanceError`.

### 31. Що означає slots=True?
**Відповідь:** Замінює стандартний динамічний словник `__dict__` фіксованим кортежем слотів `__slots__`, що зменшує споживання оперативної пам'яті та прискорює доступ до полів.

### 32. Що таке dunder method?
**Відповідь:** Спеціальний магічний метод із подвійними підкресленнями (double underscore), що інтегрує користувацький клас у стандартну об'єктну модель мови Python.

### 33. Для чого `__repr__()`?
**Відповідь:** Повертає однозначне офіційне строкове представлення об'єкта для розробника та налагодження.

### 34. Для чого `__str__()`?
**Відповідь:** Повертає зручне для читання користувачем представлення об'єкта.

### 35. Для чого `__len__()`?
**Відповідь:** Викликається вбудованою функцією `len()` для повернення розміру контейнера.

### 36. Для чого `__iter__()`?
**Відповідь:** Повертає ітератор над елементами об'єкта для використання в циклі `for` чи функціях ітерації.

### 37. Для чого `__contains__()`?
**Відповідь:** Реалізує роботу оператора перевірки входження `in`.

### 38. Для чого `__call__()`?
**Відповідь:** Дозволяє викликати екземпляр класу як звичайну функцію: `obj()`.

### 39. Що таке SOLID?
**Відповідь:** Акронім 5 основоположних принципів об'єктно-орієнтованого проектування: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion.

### 40. Що означає SRP?
**Відповідь:** Принцип єдиної відповідальності: клас повинен мати лише одну причину для зміни.

### 41. Що означає OCP?
**Відповідь:** Принцип відкритості/закритості: програмні сутності мають бути відкритими для розширення, але закритими для модифікації.

### 42. Що означає LSP?
**Відповідь:** Принцип підстановки Лісков: об'єкти підкласу мають бути взаємозамінними з об'єктами базового класу без порушення коректності програми.

### 43. Що означає ISP?
**Відповідь:** Принцип розділення інтерфейсу: клієнти не повинні залежати від методів, якими вони не користуються; краще багато вузьких інтерфейсів, ніж один широкий.

### 44. Що означає DIP?
**Відповідь:** Принцип інверсії залежностей: високорівневі модулі не повинні залежати від низькорівневих; обидва мають залежати від абстракцій.

### 45. Що таке dependency injection?
**Відповідь:** Патерн, коли залежності передаються об'єкту ззовні (через конструктор чи метод), а не створюються ним самостійно всередині.

### 46. Чому DI покращує testability?
**Відповідь:** Дозволяє легко заміняти важкі зовнішні ресурси (бази даних, мережеві сервіси) легкими mock-об'єктами в тестах.

### 47. Що таке type hint?
**Відповідь:** Анотація типів, що вказує очікуваний тип змінної, параметра чи поверненого функцією значення.

### 48. Чи перевіряє Python type hints автоматично в runtime?
**Відповідь:** Ні, інтерпретатор ігнорує type hints під час виконання; вони слугують документацією для IDE та аналізаторів типів.

### 49. Що таке static type checker?
**Відповідь:** Інструмент (наприклад, mypy, Pyright), який аналізує код до запуску без виконання програми та знаходить невідповідності типів.

### 50. Для чого mypy?
**Відповідь:** Найпопулярніший офіційний статичний типізатор для Python.

### 51. Для чого Pyright?
**Відповідь:** Швидкий статичний типізатор від Microsoft, що лежить в основі розширення Pylance у VS Code.

### 52. Що таке TypeVar?
**Відповідь:** Змінна типу в Python, яка дозволяє писати параметрично поліморфний (generic) код.

### 53. Що таке Generic?
**Відповідь:** Базовий клас для створення параметризованих типів, що працюють з різними конкретними типами без дублювання логіки.

### 54. Що означає Generic[T]?
**Відповідь:** Вказує, що клас параметризований змінною типу `T`.

### 55. Що таке bound TypeVar?
**Відповідь:** Обмеження типу зверху: `TypeVar('T', bound=SomeClass)`, яке дозволяє використовувати лише `SomeClass` або його підтипи.

### 56. Що таке constrained TypeVar?
**Відповідь:** Обмеження типу чітким фіксованим списком типів: `TypeVar('T', int, float)`.

### 57. Що таке TypedDict?
**Відповідь:** Механізм опису фіксованої структури ключів та їхніх типів для звичайних словників `dict`.

### 58. Чим TypedDict відрізняється від dataclass?
**Відповідь:** `TypedDict` під час виконання залишається звичайним словником без поведінки та методів, а `dataclass` створює повноцінний екземпляр користувацького класу.

### 59. Коли доцільно використовувати TypedDict?
**Відповідь:** Для валідації зовнішніх вхідних payload-структур (JSON, конфігураційні файли, відповіді API) перед конвертацією в доменні сутності.

### 60. Чому external payload і domain object краще розділяти?
**Відповідь:** Для ізоляції бізнес-логіки від змін у форматах зовнішніх API. Якщо зовнішній сервіс змінить назву полів JSON, це не вплине на внутрішні доменні сутності, а вимагатиме лише зміни коду перетворення (парсингу).
